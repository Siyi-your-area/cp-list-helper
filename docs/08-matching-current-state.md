# 心愿单匹配现状、指标与两阶段策略

> 更新时间：2026-07-19
> 性能目标：从文件解析到返回匹配结果，P95 ≤ 30 秒
> 质量目标：自动接受结果精确率 ≥ 95%

## 1. 当前端到端流程

### 1.1 浏览器端

入口：

- 已有清单上传：`app/exhibit/[id]/page.tsx`
- 创建清单时上传：`app/page.tsx`
- Excel 解析：`lib/excel-parser.ts`

处理顺序：

1. 浏览器 `FileReader` 读取 Excel/CSV；
2. SheetJS 找表头并提取摊位号、制品名称、作者；
3. 与当前心愿单按 `摊位号 + 制品名称` 去重；
4. 将最多 1000 条输入发送到 `POST /api/cpp/match`；
5. 根据自动接受的 CPP 结果补图片、作者、热度、详情和有料/无料；
6. 批量 insert 到 `wish_items`；
7. 展示解析、匹配、落库和总耗时。

低置信结果不会自动使用 CPP 字段：

- `review`：记录“待确认候选”，页面顶部出现统一确认入口；
- `unmatched`：在备注写入“待补充”；
- 只有 `accepted` 才写入 `matchedCPPItem`。

用户打开“待确认”后可逐条或批量处理：

- **确认匹配**：再次按候选的摊位、名称和 CPP 唯一标识核对，确认后一次性补齐 CPP 字段并保存；
- **保留原始**：不关联候选，保留上传内容并清除待确认状态；
- 弹窗同时展示“上传内容”和“CPP 候选”，避免只看到一行备注却无法判断。

### 1.2 服务端

入口：`app/api/cpp/match/route.ts`

#### 第一阶段：数据库优先

1. 解析用户清单 ID 对应的 CPP `event_id/day_id`；
2. 按输入摊位批量查询候选，避免加载整个 CPP 表；
3. 使用 `doujinshiId`、标准化摊位、拆分合并摊位、名称别名和组合评分；
4. 未接受项再按商品关键词查询 Supabase；
5. `exact/high` 自动接受，`medium/low` 进入待确认。

#### 第二阶段：外部接口兜底

仅对数据库未接受、且上传内容同时包含非空“摊位号 + 制品名称”的条目调用 allcpp 搜索接口。任一字段为空时不读取 Cookie、不创建外部任务，保持数据库阶段的待确认或未匹配结果。

- 任务按标准化后的核心制品名称去重；
- 搜索词先剥离 `【图奈】`、`【新刊】` 等开头标签及 `CP32/首发/场贩/通贩` 等宣发词，再保留真正的作品名；
- 搜索结果必须属于目标活动日；摊位不再作为硬过滤条件，而是作为低权重辅助特征，避免制品名称正确但用户摊位缺失或过期时漏匹配；
- 外部候选按“核心名称 80% + 目标活动 10% + 摊位 5% + 作者/社团 5%”评分；
- 目标活动内只有一个制品 ID 的标准化核心名称完全一致时，若上传摊位为空或与 CPP 摊位一致则直接接受；同名多个制品或已填写摊位明显冲突时仍进入人工确认；
- 非完全一致结果只有名称相似度 ≥ 95%、组合分 ≥ 90% 且领先第二候选至少 5% 才自动接受，其他结果进入人工确认或保持未匹配；
- 自动接受后读取 CPP 制品详情页，补充搜索接口没有的 `exchangeType`（有偿/无料）和 `description`；详情读取失败不影响已取得的名称、作者、封面、热度、原作、活动和摊位；
- 默认并发 6；
- 最多 40 个外部任务；
- 单请求超时 5 秒；
- 整个服务端匹配预算 28 秒；
- 到达预算后不继续外部请求，剩余条目保持待确认/未匹配。

Cloudflare 生产环境需要设置 `CPP_COOKIE` Secret，否则外部阶段会安全跳过，核心数据库匹配不受影响。本地开发可读取被 Git 忽略的 `cpp-search-request.txt` 或 `cpp-cookies.json`，但不会执行其中的 cURL 命令。

### 1.3 外部登录态安全

- Git 只保存解析和请求代码，不保存 Cookie 值；
- `.gitignore` 明确排除 `.env.local`、`.dev.vars`、`cpp-cookies.json` 和 `cpp-search-request.txt`；
- 生产 Cookie 使用交互式命令 `npx wrangler secret put CPP_COOKIE` 写入 Cloudflare Secret，不写进 `wrangler.jsonc`、源码、命令参数或 CI 日志；
- 服务端日志只记录任务数、成功数和耗时，不记录 Cookie、完整请求头或外部响应正文；
- 本地 cURL 解析只允许 `https://www.allcpp.cn`，且拒绝换行和非法 Cookie 名，文件内容不会被作为命令执行；
- Cookie 过期时外部阶段返回空结果并降级到数据库结果，不阻断心愿单导入。

## 2. 标准化与评分逻辑

代码：`lib/cpp-matcher.ts`

### 2.1 标准化

- Unicode NFKC：统一全角/半角；
- 去空白、常见中英文标点和括号；
- 转小写；
- 合并摊位拆分，例如 `伍C21伍C22` 同时索引为 `伍C21`、`伍C22`；
- `《》`、`「」`、`『』` 中的标题可作为别名；
- `【】`、`[]`、`()` 更常是 CP、社团或“新刊”标签，只剥离标签，不再把标签内容当成独立商品名；
- 生成去除 `CPxx`、`新刊`、`首发`、`场贩`、`通贩` 的名称别名。

### 2.2 特征

| 特征 | 权重 |
|---|---:|
| 摊位相似度 | 45% |
| 名称/别名相似度 | 45% |
| 作者相似度 | 10% |

唯一 `doujinshiId` 命中直接为 `exact`。

以上是数据库阶段评分。外部搜索阶段使用独立权重：

| 外部特征 | 权重 |
|---|---:|
| 核心制品名称 | 80% |
| 目标活动/日期 | 10% |
| 摊位 | 5% |
| 作者或社团 | 5% |

### 2.3 决策阈值

| 决策 | 条件 | 系统行为 |
|---|---|---|
| `exact` | 摊位完全一致且名称/别名完全一致 | 自动接受 |
| `high` | 摊位 ≥ 0.95、名称 ≥ 0.77，且候选不歧义；或作者 ≥ 0.90 且名称 ≥ 0.68 | 自动接受 |
| `medium` | 总分 ≥ 0.72，或高分但候选接近 | 待人工确认 |
| `low` | 总分 0.60–0.72 | 待人工确认 |
| `none` | 无候选或最高分 < 0.60 | 待补充 |

同一输入的前两名不同商品分差小于 0.03 时，即使分数很高也降级为待确认。

## 3. 性能指标

接口返回 `timings`：

| 字段 | 说明 |
|---|---|
| `bodyMs` | JSON 读取 |
| `scopeMs` | 清单到 CPP 范围解析 |
| `candidateQueryMs` | 摊位候选数据库查询 |
| `databaseMatchMs` | 本地索引和评分 |
| `databaseSearchMs` | 关键词数据库补查 |
| `externalMs` | 外部 API 兜底 |
| `serverTotalMs` | 服务端总耗时 |

浏览器补充：

| 字段 | 说明 |
|---|---|
| `parseMs` | Excel 解析 |
| `dedupeMs` | 当前清单去重 |
| `requestMs` | 匹配 API 网络往返 |
| `persistMs` | 心愿单批量落库 |
| `endToEndMs` | 解析开始到落库完成 |

服务端每次请求还会输出结构化日志：

```text
[CPP Match Metrics] {"eventId":"...","stats":{...},"timings":{...}}
```

## 5. 质量评测口径

运行：

```bash
npm run evaluate:matching
```

或评测完整 API：

```bash
npm run evaluate:matching -- \
  --endpoint=http://localhost:3000/api/cpp/match \
  --event=cp32 \
  --iterations=20
```

指标定义：

- 自动匹配精确率：正确自动接受数 / 所有自动接受数；
- 召回率：正确自动接受数 / 所有应匹配正样本；
- 误匹配率：错误自动接受数 / 所有自动接受数；
- 接口兜底率：由外部接口自动接受的数量 / 全部输入；
- 待确认率：`review` 数量 / 全部输入；
- P95：多次完整请求总耗时的第 95 百分位。

评测命令在以下任一条件不满足时返回非零退出码：

1. 自动匹配精确率 ≥ 95%；
2. P95 ≤ 30 秒。

## 6. 已知限制与下一步

1. 当前黄金集只有 23 条，能防回归，但不足以证明所有 CPG 数据都达到 95%。
2. CPG 上线前应建立至少 200–500 条真实人工标注样本，并按分类、活动日、摊位类型分层抽样。
3. 外部兜底已完成单个真实制品验证，但 Cookie 会过期，生产环境仍需监控登录重定向率、成功率、超时率和误匹配率。
4. Supabase `%keyword%` 查询是当前最大瓶颈。数据迁移 005 已加入标准化字段，后续可使用 `pg_trgm`/RPC 做服务端 Top-K 候选，替代多次 `ILIKE`。
5. 指标当前写入 Worker 日志和前端结果。若需要长期 P95，应新增 `match_runs` 指标表或接入 Cloudflare Analytics，按日聚合。
6. 外部接口结果当前只用于本次匹配，不自动写回 `cpp_items`。经过人工确认后再回灌更安全。
7. CPP 搜索及详情页不是本项目控制的稳定公共契约；字段或反爬规则变化时必须安全降级，不能让外部失败阻断导入。
